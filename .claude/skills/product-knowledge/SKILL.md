# Adame

Adame ("Automatic Docker Application Management Engine") manages one application running in a docker-container
on a Linux-host. An Adame-managed environment is technically a git-repository: the configuration, the
docker-compose-file, the intrusion-detection-rules and the volumes all live inside that repository, and Adame
commits every state-changing step so the history of the environment is reconstructible.

## Structure of the repository

The repository follows the "common project structure". Use the `work-with-common-project-structure`-skill when
you need the details of that structure.

There is one code-unit, `Adame`, a Python package. Almost the entire logic lives in the single class `Adame` in
`Adame/Adame/AdameCore.py` (~1400 lines). The CLI entry-point is `adame_cli()` at the end of that file, which
maps subcommands to the public methods of that class.

## Commands and the pattern behind them

Every public command (`create`, `start`, `stop`, `applyconfiguration`, `diagnosis`, `startadvanced`,
`stopadvanced`, `checkintegrity`, `exportlogs`, `checkout`) is a thin wrapper (`__execute_task`) around a
private `__`-prefixed method that does the actual work, loads the configuration first and commits the result
afterwards. All commands except `create` are meant to be idempotent and operate on an existing environment via
`--configurationfile`. `startadvanced`/`stopadvanced` are the recommended composites: they combine
stop/re-apply-configuration/save-state/start rather than being separate mechanisms of their own. Keep new
commands consistent with this wrap-load-act-commit pattern.

## Configuration files of a managed environment

An Adame-managed environment (created by `create`, see `__create_adame_configuration_file`) consists of:

- `Adame.configuration` - the main configuration (network-interface, log-target, etc.).
- `Security.configuration` - security-related settings, including the intrusion-detection-system rules.
- `Networktraffic.Custom.rules` - user-defined IDS-rules; the placeholder for the configured network-interface's
  IP is documented as `__localipaddress__`, see the discrepancy noted below.
- `Networktraffic.Generated.rules` - regenerated by `__regenerate_networktrafficgeneratedrules_filecontent` on
  every `applyconfiguration`.
- `docker-compose.yml` - free-form as long as it is valid docker-compose.

Reference documentation for these files lives in
[Configuration.md](../../../Adame/Other/Reference/ReferenceContent/Articles/Configuration.md) and command usage
in [Usage.md](../../../Adame/Other/Reference/ReferenceContent/Articles/Usage.md).

## Known gaps (do not silently "fix" as unrelated cleanup)

[Hints.md](../../../Adame/Other/Reference/ReferenceContent/Hints.md) lists findings from a prior code-review
that are intentionally not fixed yet because they need a decision or a bigger refactoring. The most relevant
when touching related code:

- `__save_metadata`/`__restore_metadata` are no-ops (permission/owner restoration across machines does not
  work), even though this is one of Adame's advertised features.
- `__run_system_command` always returns `true`, so container-start failures are logged as success.
- `_internal_container_is_running`/`_internal_ids_is_running` trust the last-written `RunningInformation.txt`
  instead of checking the real process state, so a reboot/crash leaves stale state.
- The IDS-placeholder is documented as `__localipaddress__` but implemented as `__.builtin.localipaddress.__`,
  and `__get_local_ip_address` returns a constant placeholder string instead of resolving the real address.
- `checkintegrity` always exits `0`, even when it logged integrity-warnings.

If a task touches one of these areas, treat the existing behavior as a known, tracked gap rather than an
accidental bug to silently fold into an unrelated change - mention it and ask if it should be addressed as part
of the task.

## Building and testing

`scbuildcodeunits` builds and tests everything, run from the repository root. For the single code-unit, the
scripts under `Adame/Other/Build` and `Adame/Other/QualityCheck` implement the individual steps and must be run
from the folder they are located in.

Tests live in `Adame/AdameTests/test_Adame.py` and use `EnvironmentForTest.py` plus
`Adame.set_test_mode(True)`/`_internal_register_mock_process_query` to mock the external processes (docker,
snort, git) that the real commands would otherwise invoke. Run tests with `pytest` rather than
`python -m pytest`.
